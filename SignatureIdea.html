How to trust a function’s return

  • Returns only an error → nil means success. (Execute, often ListenAndServe)
  • Returns value + error → check error, then your rules on the value. (Atoi, ParseFiles)
  • Returns nothing → side job only. (HandleFunc, Set, WriteHeader)

Act 1 — Program wakes up

NewServeMux gives an empty path → handler phone book. HandleFunc adds entries. It returns nothing.

Important: register every route before ListenAndServe. That call opens port 4000 and blocks forever. Lines below it in main never run. Empty mux → Go’s default “404 page not found” (not your custom message). Don’t fix this with go ListenAndServe then register — race.

log.Println talks to the terminal. log.Fatal logs and exits.

Run from backend/: go run ./cmd/web so both main.go and handlers.go compile, and template paths resolve.

Act 2 — A request arrives

Browser hits a URL. Go gives you r (request) and w (blank reply).

Mux matches the path only (/snippet/view). Query after ? is ignored by the router.

r.Method is a string field (GET, POST…). Prefer comparing to http.MethodGet / http.MethodPost.

Id from query: r.URL.Query().Get("id") → string. Use ?id=12 (equals). Missing / empty → "". Then Atoi → int + error. Bad or non‑positive id → your notfound (404).

Act 3 — You write the reply

  1. Labels — w.Header().Set(...)
  2. Stamp — WriteHeader (200, 404, 405…)
  3. Contents — Write / Fprintf / template

After stamp or first body write, header changes are ignored by the client. Wrong method → 405 + Allow, not 404.

Header map is always string → list of strings. Set replaces; Add appends. Those methods canonicalize names (case-insensitive).

Go may auto-add Date, Content-Length, Content-Type. Set Content-Type yourself when it matters. http.Error forces plain text.

Act 4 — Home uses templates (short)

Instead of stuffing HTML into Go strings, you load .tmpl files and pour them into w. The next section is the long version — read it slowly; this is the hard part.

Deep dive: HTML templates (CRITICAL)

Goal: understand define vs template, how base / home / nav fit together, and what blows up if two pages both define "title".

0. Requests are not always GET

Typing localhost:4000/ or clicking a normal link is usually GET. That is not a rule of HTTP. Forms, curl -X POST, etc. can send other methods. Always treat r.Method as “whatever the client sent,” and check it when the handler cares.

1. What problem templates solve

Without templates, page HTML lives in Go strings. Messy. With templates:

  • HTML lives under ui/html/
  • Go: read files → combine named pieces → write bytes into w
  • Same idea as w.Write: you’re filling the response body

2. Lowest level — define vs template

Forget files for a moment. Think named boxes of text.

define = SAVE a clip under a name (does not show anything by itself).
template "name" = PASTE that clip right here into the output. 

{{define "title"}}Home{{end}}

Means: create box "title", put the word Home inside.
Like:   title = "Home"


<title>{{template "title" .}} - Snippetbox</title>

Means: write <title>, paste box "title", write " - Snippetbox"</title>.
Result: <title>Home - Snippetbox</title>

Analogy to normal code: define ≈ assign a variable; template ≈ print that variable. If you only define and never template, nothing appears. If you template a name that was never defined → error at execute time.

In the fileJob
{{define "base"}}…{{end}} Save this whole layout as box base.
{{define "title"}}Home{{end}} Save box title = Home.
{{define "main"}}…{{end}} Save box main = page body HTML.
{{define "nav"}}…{{end}} Save box nav = navigation HTML.
{{template "nav" .}} Paste box nav here.
. Data from Go. nil for now = no dynamic data.

3. Your three files — who saves, who pastes

  • base.tmpl — defines base (the frame). It pastes title, nav, main. Shared style/layout for every page.
  • partials/nav.tmpl — only defines nav. Shared links.
  • pages/home.tmpl — only defines title + main for the home page.
After ParseFiles(base, home, nav), the bag of boxes is:

  "base"  → full HTML skeleton with holes
  "nav"   → <nav><a href="/">Home</a></nav>
  "title" → Home
  "main"  → Latest Snippets block

ExecuteTemplate(..., "base", ...):
  start writing base
    → hit {{template "title"}} → paste Home
    → hit {{template "nav"}}   → paste nav
    → hit {{template "main"}}  → paste main
  → finished page goes into w → browser

Later you’ll add view.tmpl the same way as home: its own define "title" and define "main", still using the same base + nav.

4. CRITICAL — two pages both defining "title"

All names from one ParseFiles call share one bag. There is only one slot called "title".

If home.tmpl and view.tmpl both define "title" and you parse both into the same files array, the last file wins. Silent overwrite. You may show the wrong title. Go does not always scream “duplicate define.” 

CORRECT (book style) — one page per handler:

  home() → ParseFiles(base, nav, home.tmpl)
  view() → ParseFiles(base, nav, view.tmpl)

WRONG for home():

  ParseFiles(base, nav, home.tmpl, view.tmpl)
  → both define "title" / "main" → last one overwrites

Not parsing view.tmpl inside home() is correct. Home does not need view’s boxes. Files sitting on disk do nothing until ParseFiles reads them for that request.

SituationWhat happens
base pastes "title" but no define "title" in the set ExecuteTemplate returns an error → your notAvailable
File path wrong / missing ParseFiles returns an error
Two defines of "title" in same ParseFiles Last wins — wrong content possible, often no loud duplicate error
view.tmpl exists but not in home’s files list Fine — ignored for this request

5. How Go “knows” home (it doesn’t by filename)

main.go:
  HandleFunc("/{$}", home)     // URL "/" → run function home

handlers.go home():
  ParseFiles(base, home.tmpl, nav)   // YOU listed these files
  ExecuteTemplate(w, "base", nil)    // start at box "base"

The word Home in the browser tab comes from define "title" in home.tmpl, not from the Go function name. The function name home is only tied to the route because main registered it.

6. What the handler does (line by line)

files := []string{
    "./ui/html/base.tmpl",
    "./ui/html/pages/home.tmpl",
    "./ui/html/partials/nav.tmpl",
}
tmpl, err := template.ParseFiles(files...)
err = tmpl.ExecuteTemplate(w, "base", nil)

ParseFiles(filenames ...string) (*Template, error)

  • Opens each path (cwd-relative).
  • Runs every define → fills the bag of boxes.
  • Missing file → error. Do log.Print(err).

ExecuteTemplate(w, "base", nil) error

  • w — already a response pipe from the server; this writes HTML into it.
  • "base" — start at that named box (prefer this over plain Execute).
  • nil — no dynamic data yet.
  • Only returns error. nil means the page was written.

w is not “empty until Write.” Every successful ExecuteTemplate is already sending body bytes through w. A later w.Write("Hello…") only appends junk after </html>.

7. cwd, links, port

  • Run from backend/: go run ./cmd/web so ./ui/... resolves.
  • href="/" means “same site, path /”. Browser already on localhost:4000 → hover shows that. No port in the tmpl file.

One breath: define = save clip; template = paste clip; base = layout that pastes; each page tmpl = that page’s title/main; ParseFiles only base+nav+that page or titles overwrite; ExecuteTemplate("base") writes into w.

Project shape (short)

cmd/web = app you run. ui/ = templates. internal/ = private packages (special folder name; only code under its parent may import them — not a language keyword).
