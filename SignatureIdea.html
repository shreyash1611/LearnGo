SignatureIdea

Not an API manual. A walk through what happens when someone hits your Snippetbox app — and what each built-in call is doing along the way.

The only rule that keeps confusing you

Every function tells you how to trust it by what it returns.

  • Returns only an error → if the error is empty (nil), it worked. That’s the whole check. (Execute is like this.)
  • Returns a value and an error → check the error, then decide if the value is acceptable. (Atoi is like this.)
  • Returns nothing → it just does a side job: set a header, register a route, print a log line.

Act 1 — Your program wakes up

In main, you build a router with NewServeMux. That gives you an empty “phone book” of paths.

HandleFunc adds entries to that book: “when the path is this, call that function.” It doesn’t answer browsers itself. It returns nothing.

ListenAndServe opens the door on port 4000 and waits forever. You only get an error back if the door won’t open (port busy, etc.). log.Println is just you talking to the terminal; log.Fatal talks and then kills the program.

Act 2 — A request arrives

Someone visits a URL. Go fills in r (the request) and gives you w (the blank reply form).

The mux looks at the path only (/snippet/view). Everything after ? is ignored by the router. That’s why you never registered id on the mux.

Your handler runs. r.Method is a plain string field — GET, POST, and so on. No function call.

For the id, you ask the URL’s query string: r.URL.Query().Get("id"). That always gives a string. Missing id → empty string, not an error. Then Atoi tries to turn that string into a number. Bad text → error. Good number that’s still useless (zero, negative) → you reject it yourself.

Act 3 — You write the reply

Think of the reply as a package:

  1. Labels on the box — headers via w.Header().Set(...)
  2. Stamp — status via WriteHeader (200, 404, 405…)
  3. What’s inside — body via Write or Fprintf

Once you stamp or put something in the box, you can’t change the labels anymore. Set headers first.

http.Error is a shortcut: it stamps an error status and writes a plain-text message for you. Returns nothing. It also forces the content type to plain text — so don’t expect JSON after calling it.

Act 4 — Home page with a template

ParseFiles reads your .tmpl file from disk. You get a template object and an error (file missing, etc.).

Execute pours that template into w. It only returns an error. There is no second “did it look valid?” value — the HTML either got written or it didn’t. That’s why the book only checks err.

Pocket glossary

w — ResponseWriter
The reply you’re building for the client.
r — Request
What the client sent (method, path, query, body).
mux — ServeMux
Path → handler phone book.
Template
Parsed HTML file ready to fill and send.
